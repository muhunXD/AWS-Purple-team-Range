# T1552.005 — Credentials from Instance Metadata

Catches EC2 instance role credentials being used from somewhere that is not the
instance they belong to.

Detonated `2026-08-20 12:29:54 UTC` in `ap-southeast-1` using
`aws.credential-access.ec2-steal-instance-credentials`.

```
fields @timestamp, eventName, userIdentity.arn, sourceIPAddress, userIdentity.type
| filter userIdentity.arn like /assumed-role/
| filter userIdentity.arn like /i-/
| filter sourceIPAddress not like /amazonaws/
| stats count(*) as calls, earliest(@timestamp) as first_seen
    by userIdentity.arn, sourceIPAddress
| sort calls desc
```

An instance role session is easy to spot because the ARN ends with the instance ID, like
`assumed-role/stratus-red-team-ec2-steal-credentials-role/i-05abb3024e11f8e64`. When the
instance uses its own role the calls come from an AWS IP. In the detonation the exact
same role appeared from `46.137.224.18` (the instance) and from `<MY_IP>` (my
laptop) inside the same minute. Same role, two IPs, one of them outside AWS — that is
the credentials having left the instance.

| Detonation window | Clean window |
|---|---|
| Fired — 2 calls from the external IP | Did not fire |

False positives should be rare here. My normal SSO admin role is not an instance role so
it never matches. In a real environment NAT gateways or proxies could make instance
traffic look external, so a production version of this would allowlist known egress IPs
instead of just excluding `amazonaws`.

This is the detection I want to race GuardDuty on, since
`UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration` covers the same behaviour.
