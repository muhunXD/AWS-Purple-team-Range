# T1098.001 — Additional Cloud Credentials (Console Password)

> Note on numbering: Stratus Red Team categorizes this attack under the Privilege
> Escalation / Persistence tactics without publishing a specific sub-technique number. The
> underlying behaviour — giving an identity a new way to authenticate as a persistence
> mechanism — is the same ATT&CK sub-technique as `T1098.001-backdoor-user.md`, just via a
> console password (`UpdateLoginProfile`) instead of an access key (`CreateAccessKey`). It's
> filed under the same ID for that reason, with a distinct filename per procedure.

Catches an IAM user's console password being set or changed — a way to hijack or backdoor
console access to an identity, separate from the access-key persistence already covered above.

Detonated `2026-08-26 ~17:41 UTC` using `aws.privilege-escalation.iam-update-user-login-profile`.
IAM is a global service, so — same as the access-key variant of this technique — the event lands
in `us-east-1` regardless of which region the range runs in.

```
fields @timestamp, eventName, userIdentity.arn, requestParameters.userName, sourceIPAddress
| filter eventName = "UpdateLoginProfile"
| sort @timestamp desc
| limit 50
```

The Stratus log shows the console password for `stratus-red-team-update-login-profile-user`
being set, followed immediately by a login URL and the new (plaintext, in the tool's own output)
password. `UpdateLoginProfile` is the exact CloudTrail event name for this action, and it records
the target `userName` in `requestParameters` — the same shape of signal as the `CreateAccessKey`
detection: worth checking whether the caller is resetting their *own* password (routine) or
someone else's (worth a second look).

| Detonation window | Clean window |
|---|---|
| Fired — `UpdateLoginProfile` on `stratus-red-team-update-login-profile-user` | Did not fire |

Same false-positive profile as the access-key backdoor detection: legitimate password resets
(self-service or admin-assisted) produce an identical event. This is a review trigger, not
something to auto-block — correlate against a help-desk ticket or an approved admin action
before treating it as compromise.

This detection currently only exists as a retrospective query; unlike `CreateAccessKey`, there is
no live metric filter/alarm wired up for `UpdateLoginProfile` yet. Adding one would be a natural
extension of `terraform/logging/responders.tf`.
