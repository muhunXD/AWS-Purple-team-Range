# T1136.003 — Create Cloud Account

Catches a new IAM user being created and immediately given admin permissions and
programmatic access.

Detonated `2026-08-20 <FILL IN> UTC` in `us-east-1` using
`aws.persistence.iam-create-admin-user`.

```
fields @timestamp, eventName, requestParameters.userName, requestParameters.policyArn, userIdentity.arn, sourceIPAddress
| filter eventName in ["CreateUser","AttachUserPolicy","CreateAccessKey"]
| sort @timestamp asc
| limit 50
```

Any one of these three events on its own is normal. What makes it a technique is the
sequence and the speed: `CreateUser`, then `AttachUserPolicy` pointing at
`arn:aws:iam::aws:policy/AdministratorAccess`, then `CreateAccessKey`, all within a
minute or two. That is a brand new identity being handed full control of the account
plus a way to use it from anywhere.

| Detonation window | Clean window |
|---|---|
| Fired — full sequence on the new user | Did not fire |

The false positive risk is the same as the backdoor detection: legitimate user
provisioning follows the same steps. The difference is the policy ARN. Filtering
specifically on `AdministratorAccess` rather than any attached policy cuts most of the
noise, since granting full admin to a fresh user is rare and should be reviewed even
when it is legitimate.

Sorting ascending here is deliberate. Reading the events oldest first makes the sequence
obvious, which is the whole point of this detection.
